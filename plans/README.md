# Implementation Plans — Kessel Run Skills App

Generated by the improve skill on 2026-07-29 (`plan` variant — no audit was run).
Last reconciled 2026-07-30 against commit `6e39653`.

**Goal**: turn the 11 Kessel Run content-pipeline skills in `kessel-run-skills/`
into a working Next.js app — the skills installed into Mastra using Mastra's
first-class skills primitive, driven by a shadcn-based user interface, with
pipeline artifacts carried from stage to stage.

## Decisions already made (do not re-litigate)

These were chosen by the repo owner. Plans assume them.

1. **Skill routing — pinned picker + auto-load.** The UI pins one skill per
   session via Mastra's dynamic `skills` resolver reading `requestContext`.
   The agent may still load a sibling skill mid-conversation (e.g. Anchor
   handing off to Ideation).
2. **Pipeline state — project model.** A "content project" holds the anchor,
   ideation map, hook, beat map, and draft. Later stages receive earlier
   outputs automatically. Implemented with Mastra schema-typed working memory.
3. **UI — shadcn.** Already configured in this repo (`components.json`,
   `src/components/ui/`, style `base-nova`, base color `neutral`).
4. **One agent, eleven skills** — not eleven agents. This is what Mastra's
   skills primitive is for: progressive disclosure, one memory/tool config,
   and continuity across stages inside a single thread.

## Scope boundaries that apply to every plan

- **Do not touch `src/components/ai-elements/` or `src/components/ui/`** except
  to add new shadcn components via the CLI. These are vendored library code
  that carries hand-applied compatibility fixes; re-running `npx ai-elements`
  would overwrite them. Build app UI in `src/components/kessel-run/` instead.
- **Do not delete the weather agent, tool, or workflow** (`src/mastra/agents/weather-agent.ts`,
  `src/mastra/tools/weather-tool.ts`, `src/mastra/workflows/weather-workflow.ts`)
  or the `/chat` page and `/api/chat` route. They are the working reference
  implementation from the Mastra Next.js guide and are useful for isolating
  whether a failure is in Mastra or in the new code.
- **Do not commit `.env`, `mastra.db*`, or `mastra.duckdb*`.** Already gitignored.

## Findings considered and rejected

- **Model each of the 11 skills as its own Mastra Agent.** Rejected: duplicates
  memory/model/tool config eleven times, and breaks pipeline continuity because
  each agent would own a separate thread. Mastra's `skills` primitive exists
  precisely to avoid this.
- **Model the pipeline as a Mastra Workflow with suspend/resume.** Rejected for
  now: the stages are open-ended conversations, not steps with typed inputs and
  a fixed order — the QUICK-REFERENCE lists five different valid stage orders
  depending on content format. A workflow would fight that. Revisit only if a
  fully unattended batch mode is ever wanted.
- **Store pipeline artifacts in a separate LibSQL table.** Rejected: Mastra
  schema-typed working memory already does this, is scoped to the thread, is
  readable via `memory.getWorkingMemory()`, and the agent can update it through
  a built-in tool with no custom write path to secure.
- **Convert the skills to inline `createSkill()` calls.** Rejected as the
  primary approach: it would fork the markdown into TypeScript template
  literals and guarantee drift from the source files. Filesystem skills keep
  the markdown canonical. See plan 002 for the deployment caveat this creates
  and how it is handled.
